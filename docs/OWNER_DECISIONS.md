# Owner decisions — EMS corpus open questions

Answered by the owner (Stamate Viorel) in a quiz session, 2026-08-02.
These are **owner decisions in a reference implementation**, not thread consensus.
Rejected alternatives are preserved so a maintainer can overturn any of them.

The questions these answer, the options put alongside them and the evidence each
recommendation rested on are in [`DECISIONS_PENDING.md`](DECISIONS_PENDING.md), kept as the
historical record of how the pass was framed. Three answers below departed from the
recommendation made there — D1, D10 and D11, the last two both from its row A5 — and one of
its recommendations (A14's shed threshold) was transcribed with a sign error that the corpus
corrects; that page's own header says so.

| # | Question | Decision | Notes |
|---|---|---|---|
| D1 | Master stop: halt dispatch only, or evaluation too? (EC-6, part of pack A3) | **Halt everything** — no contributed algorithm is invoked while stopped | **Owner override of the pack**, which recommended dispatch-only. Owner's rationale: a stopped engine still running third-party algorithms means "stopped" stopped the engine's writes, not the site's; relying on add-ons to no-op is exactly what a kill switch must not assume. Pack's alternative (dispatch-only, `stopped` exposed in context, "a stopped engine is a black box when you need to know why you stopped it") preserved. |
| D2 | Fridge past max-off vs fuse headroom — who wins? (EC-5, pack A3 ladder) | **electrical limits > device protections > level gates > optimization** | Confirmed independently by the pack and by the owner's own binding: `constrainOnOff` javadoc — "the fuse outranks the freezer, deliberately". Master stop sits above the whole ladder (D1). |
| D3 | Shadow and stop: one control or two? Fresh-install state? (pack A3) | **Two controls; fresh install = shadowed, stop disengaged** | Shadow = compute+log, write nothing (global + per-algorithm + per-participant). Stop = halt everything (D1). Matches the two-control shape already shipping in the owner's binding, which is what staged his live cutover. |
| D4 | Priority direction, default, tie-break (pack A2) | **Lower number = better, in BOTH senses** (served first AND wins conflicts); default 100; tie-break by participant id ascending (stateless) | ⚠️ FOLLOW-ON: the live emsmanager `Controller` contract says "lower runs first, higher wins on conflict" — contradictory — so the binding needs reconciling. Several algorithms may be active at once. Priority is a rank (lower=better); the level scale is a magnitude (higher=more available) — deliberately NOT forced to point the same way. Pack retracted its own wrong claim that `buildEngineDispatchSet` proved lower-wins. |
| D5 | Declaration mechanism, identity, precedence (pack A1) | **Both mechanisms behind one provider SPI**; identity = **Item name** (overridable by explicit id); a duplicate is a further statement about the same participant, never a second one and never an error; precedence **explicit metadata > contributed (ties by service.ranking) > discovered proposal** | This answers Kai's flagship open question. Exception kept: the write-side actuation sink is chosen by explicit configuration naming it, never by ranking. Evidence: core `MetadataKey` is already (namespace, itemName); `StateDescriptionServiceImpl` is core's ranked-aggregator precedent; owner's `MetadataParticipantScanner` already does metadata-wins-on-duplicate. |
| D6 | Which way does the level dependency run? (EC-4d / I1, cross-cutting) | **The engine computes the level from its own snapshot** — the level plane is a pure function it calls, not a service it reads | Resolves a genuine circularity: the two changes referenced each other and neither mentioned the other. Guarantees level and readings cannot disagree within one cycle, which is what makes "one consistent snapshot per cycle" true. Matches what the prototype had to do to compile (it reported this as removing a contradiction, not as an answer). Alternative preserved: level published separately as Item + planned TimeSeries (closer to masipila's planned-vs-current split) — if adopted later, publication becomes an output of the engine, not its input. |
| D7 | Where do protection timers (minOn/maxOn/minOff/maxOff) measure elapsed time from? (EC-4c / N3) | **Device state history via the persistence service** | The spec flagged this as "a safety choice, not an implementation detail — it decides whether a compressor's cooldown survives a restart". REQUIREMENT THIS CREATES: the engine must detect when history is unreadable (site doesn't persist that item) and report it, never silently assume zero elapsed. Precedent in the owner's binding: CostAnalytics restores from persisted items across restarts. Alternatives preserved: engine memory only (forgets on restart); engine memory with unknown treated as full-wait (fail-safe but idles devices after every restart). |
| D8 | Acknowledgement: what counts, and what does expiry mean? (EC-3b / EC-3c) | **Tolerance band counts as acknowledgement; on expiry the command lapses and control resumes** | The spec's own example: "Is 15.999 A an acknowledgement of 16 A? — a tolerance is a number, and no requirement carries one." Grounded in the owner's live hardware: OCPP chargers report lagging, imprecise values, which is why the binding has an ACK window at all. STILL TO SET (Part B parameter): the tolerance value and the window length. Alternative preserved: the "safety-conservative reading" — a device that never acknowledges is withheld from further commands until cleared (cost: a flaky charger silently drops out of management). |
| D9 | Trim or defer, and who decides? (EC-8 / E13) | **The load's own shape decides** — switch = defer only; continuous = trim to boundary; trimming below a declared minimum becomes deferral; a Batch programme mid-run is exempt (the taxonomy forbids interrupting it) | Priority decides the ORDER loads are acted on; shape decides WHAT happens to each. Requires no new user declaration. Close to the prototype's behaviour (trim to boundary unless it breaks the declared minimum, then defer) — but now stated as the rule rather than as one reading among several. Alternatives preserved: per-participant declared preference; explicit per-profile-class rule. Note the spec's warning this resolves: with Batch exempt, "either the rule or the taxonomy has to give" is settled in the taxonomy's favour. |
| D10 | What counts as surplus? (EC-11 / E7) | **Grid export + battery charging that can be reclaimed** | Battery charging is a decision the EMS itself made, not a fixed load, so it is available to a higher-priority consumer. Matches real behaviour on the owner's site: solar-first EV charging that ignored battery charging would idle while the battery absorbed everything. Alternatives preserved: grid-export-only (what the prototype used — unambiguous but a 3 kW battery charge hides all surplus); export + battery + curtailed PV (most complete, but needs inverter curtailment reporting that many lack). OPEN SUB-QUESTIONS still to settle in Part B: instantaneous vs averaged vs forecast surplus; whether an already-running managed consumer's own draw counts. |
| D11 | Sign conventions beyond the grid reading (E6 — the blocker for D10) | **Fixed in the spec, one convention: grid + = export, battery + = charging, PV + = producing, consumers + = consuming; a battery setpoint takes the same sign as its reading (+ = charge)** | Devices that disagree are normalised at the edge with invert flags. This unblocks D10 — the spec flags E6 as a hard blocker: surplus cannot be computed at all until signs are defined for every role and for setpoints, not just the grid. Grounded in the owner's binding, which already normalises exactly this way (invertGrid/invertSolar/invertHouse/invertBattery in one layer) because real inverters disagree — and in the site's own Weinzierl/Solis unsigned-register wrap issue. Alternatives preserved: per-participant declared conventions; readings-only fixed with per-device setpoint direction. |
| D12 | Do the four levels get fixed numbers? (L1, pack A11) | **Yes — blocked=0, normal=1, encouraged=2, overcapacity=3, fixed centrally, with the SG-ready 1–4 offset stated explicitly** | Matches what the corpus fixtures already encode, so no fixture rewrite. Every component round-trips identically and nobody guesses whether level 3 means SG mode 3 or 4. Alternatives preserved: names normative with per-exchange encodings (avoids core blessing a numbering, but a silent mismatch would invert blocked and overcapacity — the worst failure); adopt SG-ready 1–4 directly (standard, but rewrites every fixture and maps awkwardly onto non-SG devices). |
| D13 | Can a contributed script override a user's "hands off" or level gate? (pack A9 — the security boundary) | **No. Prohibitions are engine-owned; preferences are algorithm inputs** | Engine-owned and closed: the `never` flag, the user-declared per-consumer level gate, the readiness interlock, device protections, and which readings count as safety inputs (a contributor may not claim that status for itself). Overridable: the engine's OWN level-derived steering, so a planner can lift the engine's gate under deadline pressure. ALSO DECIDED: lift `never` off the Simple profile onto the consumer, so it applies to all four classes — otherwise an EV or dishwasher cannot be marked hands-off and users fake it by deleting the declaration, which also deletes the measurement the limit floor needs. Grounded in the owner's binding: gating lives in the asset handler below every controller, "the last line before an item is written". |
| D14 | Safe state when a safety input goes stale (pack A15) | **Freeze and floor** — refuse increases, floor Controllable at declared minimum, ModeControllable to most-restricted, Simple off; all subject to device protections; never interrupt a running Batch | Staleness = optional per-participant max age PLUS unreadable/UNDEF/NULL always tripping; no new age mechanism invented — a site may use core's `expire` namespace to turn a frozen item into UNDEF. Matches live site behaviour: PowerTag bridge dead → all chargers cap at 6 A. Alternatives preserved: pause everything ("how a user learns to uninstall an EMS"); keep running on last known values (cannot tell a 5-second gap from a 5-hour one). |
| D7+ | REFINEMENT of D7 by pack A15 (better-grounded mechanism) | Elapsed time comes from **`Item.getLastStateChange()`**; when null, **start the clock at first observation** and report the participant as protection-unknown; **the engine keeps no protection timers of its own** | Core already answers this: `Item.getLastStateChange()` (Item.java:77) and `PersistenceManagerImpl.restoreItemStateOnStartup` restores it explicitly — so a compressor's cooldown survives a restart **iff the item is persisted with `restoreOnStartup`**. REQUIRED SPEC CLAUSE: the engine must REPORT a protected participant whose state is not persisted, so a degraded guarantee is visible rather than assumed. DEPARTURE from the owner's binding: `constrainOnOff` currently leaves desired state untouched when `minutesInState` is NaN. Also restates mstormi's "forced restart" clause observably: an uncommanded OFF→ON transition starts minimum-runtime exactly as an engine-initiated start would. |
| D15 | What power figure does the floor book, and from where? (pack A6) | **A device may declare an Item carrying live power; prefer measurement over estimate EXCEPT when admitting a not-yet-running load.** Controllable → declared max; Batch → rated × curve; Simple → declared `ratedPower`, **optional**, falling back to the on-threshold only if absent and reporting that as a gap (never a rejection); ModeControllable → exempt. Re-book from scratch every cycle, no carried reserve | `ratedPower` is optional precisely so it does not invalidate the owner's live Simple declarations. Mode exemption grounded: an SG-ready mode 3 draws whatever the heat pump wants, so a declared number would be fiction. Alternatives preserved: reuse the on-threshold as the rating (silently over-books, thresholds carry margin); measure-only (can never reserve room to START anything). |
| D16 | Last five load-bearing items (pack A8, A10, A12, A13, A14) | **All five recommendations accepted as written** | A8 observability: outcome enum + reason on every decision, published as deduplicated events, one status Item, malformed declaration skips the WHOLE participant via `ConfigStatusProvider` (never partial-accept, never default to Simple). A10 units: watts or amps accepted, watts canonical, `[min,max]` mandatory for controllable providers, phases = integer 1/2/3. A12 windows: requests carry a `Duration`, one `cost(window, weights)` with flat weights default, windows start on slot boundaries (documented restriction), partial answers always returned with requested-vs-granted. A13 curves: the curve belongs to the PROFILE, stored relative-time, becomes a TimeSeries when scheduled, LEFT Riemann integration. A14 capacity tariff: denominated in the BILLED quantity, zone-local metering quarters not a rolling window, minimum-billable floor + month-to-date peak as free budget; grid-constraints owns look-ahead, engine-contract owns the runtime floor only. |
| D17 | Part B — 30 reversible parameters and defaults | **All accepted as recommended**, written into the spec as stated defaults | Reversible by construction: each is a configuration value, so a wrong default costs a config edit rather than a redesign. Revisit once something is running and the behaviour is visible. |

Most overturnable decision in the set. |
